# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See also `AGENTS.md` (style/commit conventions) and `README.md` (full env var table, tool behavior, deployment limits).

## Commands

Backend (Python 3.12+, uv) — run from `backend/`:

```bash
uv sync --locked                                  # install (incl. dev group: pytest)
uv run uvicorn app.main:app --reload --port 8000  # API + Band listeners
uv run python -m app.worker                       # durable task worker (separate process, required for agents to answer)
uv run pytest                                     # full offline suite
uv run pytest tests/test_tasks.py::test_name -q   # single test
```

Frontend (Node 20+) — run from `frontend/`:

```bash
npm ci
npm run dev     # Vite on :5173, proxies /api and /ws to :8000
npm run build   # tsc type-check + vite build to dist/ (served by FastAPI if present)
npm test        # offline document-link, worker, and syntax-loader regression tests
```

There is no linter/formatter. Frontend regression tests use Node's built-in runner; `npm run build` checks TypeScript, the UI catalogue, bundle budgets, and the compiled diagram worker.

## Architecture

Three processes share one SQLite app DB (`backend/band_slack.db`) and must share the same `.env` (repo root `.env` is loaded first, then `backend/.env`), especially `APP_SECRET` (encrypts stored Band agent keys):

1. **API** (`main.py` → `api/http.py` → `workspace/service.py`): REST + WebSocket. `service.startup()` syncs Band rooms/agents (`band/org.py`, Band Human API), starts a Band poller, and starts `_watch_task_messages`, which polls the DB for worker-written reply messages and pushes them to clients via the in-process `EventBus` (`workspace/events.py`). The API never runs LLM reasoning.
2. **Band listeners** (`band/listener.py`, inside the API process): `AgentManager` runs one Band `Agent` per visible agent using `QueuedAgentAdapter`, which only *enqueues* a job (`tasks.enqueue`) and returns. It suppresses Band echoes of app-originated messages (those already enqueued with source id `app-message-<id>`).
3. **Worker** (`tasks/worker.py`, started with `python -m app.worker`): `run_queue()` runs up to `WORKER_CONCURRENCY` jobs at once, each `next_task()` → `process()` → `execute()` → `complete()`, plus `deliver()` jobs. `next_task()` skips agents already running in the same channel, so each agent stays ordered per channel. Teammate hand-offs (`ask_teammate` → `tasks.hand_off`, linked in `TaskHandoff`) queue the teammate's task; `complete()` queues the report-back follow-up in the same transaction. Holds an exclusive file lock on `<checkpoint>.worker.lock` (only one worker per checkpoint file). On start, `recover_tasks()` requeues `running` tasks and marks in-flight `sending` deliveries as `unknown` (Band replies are never blindly resent).

Key cross-cutting invariants:

- **Agent skills** (`api/skills.py`, `workspace/skills.py`, `runtime/skills.py`): admins manage a shared `SkillDefinition` library and per-agent `AgentSkill` assignments from Members → agent → Skills. Validated single-skill Markdown/folder/ZIP imports preserve bounded UTF-8 supporting files without extracting or executing them. New harnesses mount enabled skills read-only at `/skills/` with native Deep Agents progressive disclosure; internal helpers inherit the mount. Skills cannot grant tools or bypass approvals. Deleting an agent clears assignments; deleting a custom library skill clears all its assignments. Built-in examples are immutable. Changes broadcast a content-free `skills_changed` event.

- **Durable queue** (`tasks/queue.py`, `AgentTask` in `persistence/models.py`): jobs are deduplicated by `source_key = "{agent_id}:{room_id}:{source_id}"` (unique). Local `@mention` messages create their job in the same transaction as the message.
- **Checkpointed execution**: each task's LangGraph thread id is the task id; checkpoints live in a separate SQLite file (`AGENT_CHECKPOINT_PATH`, `AsyncSqliteSaver`). `execute()` resumes from existing state rather than re-sending input. Cancellation is cooperative via `cancel_requested` polled every 0.5s; shutdown (`CancelledError`) intentionally leaves tasks `running` for recovery rather than failing them.
- **Harness** (`runtime/harness.py`): `create_deep_agent` with fixed internal subagents in `runtime/helpers/` (general-purpose, researcher, coder, computer, critic), each with a `ModelCallLimitMiddleware` cap. Role prompts come from `workspace/roles.py`; the model is `ChatOpenAI(model, use_responses_api=True, store=False)` unless a `model=` is injected (tests do this). Internal helpers are not Band identities; "visible teammates" are separate `AgentProfile`s with their own Band agent.
- **Tools** (`runtime/tools/`): `tools_for(task, computer)` builds task-scoped tools (channel history, keyed memory scoped to agent+channel, Exa web search and `fetch_page`, `ask_teammate`, `request_approval`, schedule tools, E2B tools). Missing API keys yield explicit "unavailable" tool results rather than errors. MCP tools (`runtime/tools/mcp.py`, config at `MCP_CONFIG_PATH`) are loaded per attempt and passed to `build_harness(extra_tools=...)`. With `COMPOSIO_API_KEY`, that load also mounts one workspace Composio session (`runtime/tools/composio.py`): agents see the search, schema, and execute meta-tools, and `AgentPluginAccess` limits which apps an agent may execute.
- **Hosted code execution** (`runtime/tools/hosted.py`): OpenAI's `code_interpreter` server tool is passed as a tool dict to the parent and the coder and critic helpers (`FAST_CODE_EXECUTION`). It runs inside the model call, so its blocks appear in message content, not `tool_calls`; `drafts.answer_text` drops text written before the last server tool block.
- **Streaming drafts** (`tasks/drafts.py`): `_execute_on_computer` streams `["updates", "messages"]` and feeds root-namespace `model` tokens to a `Draft`, which writes the `MessageDraft` row (throttled) and resets on tool calls. Only tasks whose reply goes to humans stream. `complete()` deletes the draft in the reply transaction; `process()` clears it on failure, cancel, and approval pauses. `_watch_task_messages` publishes `draft` events (content `""` means removed).
- **Growing the team** (`tasks/teammates.py`): the worker can't register Band agents, so Master's `create_teammate` inserts a `TeammateRequest` (unique per task + tool call id) and polls it; the API's `_watch_teammate_requests` claims `pending` → `creating`, calls `create_agent(..., created_by_agent=...)`, and marks it `created`/`failed`. The watcher starts only after Band connects, and `settle_interrupted()` resolves requests a restart or cancel left `creating`. Unclaimed requests expire to `failed` so the API never creates a teammate after the agent gave up. Outside Band agents are `OutsideAgent` rows per channel; `ask_teammate` routes to `ask_outside`, which records an `OutsideHandoff` and sends at most once through Band with the asking agent's key (`unknown` on an unconfirmed send or an interrupted one; `recover_tasks()` turns leftover `sending` rows `unknown`). Their replies arrive through the Band poller, and come back as a task only if they mention our agent; that task is linked (`TaskHandoff` kind `report`) to the asking request, so local and outside hand-offs share its `MAX_HANDOFFS` budget.
- **Reply components** (`runtime/tools/components.py`): `show_table`, `show_chart`, and `show_spec` validate their args (Pydantic schemas mirroring the Tool UI element props) and insert a `MessageComponent` row (unique per task + tool call id, camelCase props). `complete()` sets its `message_id` in the reply transaction; `serialize_message` carries `components` via `components_for()` in the messages API and `_watch_task_messages`. Band gets text only.
- **Generative UI** (`runtime/ui.py`, `runtime/ui_catalog.json`, `runtime/tools/generative.py`, `tasks/inputs.py`, `api/generative.py`): `ui_catalog` exposes the installed assistant-ui vocabulary, `present_ui` attaches composed replies, and `ask_user` validates the UI then calls native LangGraph `interrupt()` with a typed `user_input` payload. No writes precede the interrupt. `await_approval()` publishes a `TaskInput` (interrupt id) and linked input component in the same transaction that parks the task; replay cannot duplicate the card. `approval_decisions()` combines input answers and approval decisions by interrupt id. `ComponentResponse.component_id` claims one shared response; input validation, a human message, answered status and requeue of the original task commit atomically. Requeue waits for all inputs and approvals. The worker resumes the original checkpoint with `Command(resume=...)`, and waiting uses no worker slot. Cancellation closes inputs without inventing a response; explicit retry returns to the checkpoint. The API enforces membership and DM ownership, broadcasts receipts, and never turns submitted mentions into new agent tasks. Approvals remain separate. `GET /api/channels/{id}/views` and `read_views` reopen saved `ui` and legacy `view` components. The old form response endpoint remains for existing cards; `show_form` is no longer offered to agents. Frontend interaction state/API calls live in `AssistantUI`; catalogue elements stay presentational. `frontend/scripts/export-ui-catalog.mjs` generates the Python contract from the installed package; `npm run ui:check` in the frontend build prevents drift. Catalogue styles are scoped in `app.css`; maps and diagrams load on demand.
- **Approvals**: `request_approval` and non-read-only MCP tools call LangGraph `interrupt()`. `execute()` raises `ApprovalRequired`; `process()` records `TaskApproval` rows and sets the task `waiting` (no worker slot). `decide_approval()` requeues it, and `execute()` resumes with `Command(resume={interrupt_id: decision})`. The request message (`band_message_id` `approval:<id>`) is serialized with its `approval` state and rendered as an inline card; deciding or cancelling republishes it as a `message_updated` event.
- **Roles and policies** (`workspace/permissions.py`): `WorkspaceRole` rows hold owners and admins (no row = member); `ensure_owner()` (startup and signup) makes the oldest account the owner. `ChannelPolicy` (no row = members) gates approval decisions and cancelling waiting tasks (`approvers`), and live links, hand-back, and stopping computers (`computer_control`). The proxy routes watchers to a separate view-only VNC server; only the current take-over owner reaches the interactive server. Every client frame rechecks access and ownership; periodic checks also close idle connections when access changes. Deleting agents, model changes, policies, roles (owner only), and budgets need an admin. The frontend mirrors this with `isAdmin`/`policyBlock` in `store.ts`, kept in sync by `workspace_role` events and the channel's `policy`.
- **Activity log** (`workspace/audit.py`): `record()` / `record_agent()` add `AuditEvent` rows, inside the caller's transaction when given `session`. Values pass through `summarize()` (truncated; secret-named keys hidden at any depth and `SECRET_PATTERNS` masked in text: tokens, URL credentials, auth headers, password flags) and `summarize_args()`. The channel audit endpoint needs channel membership. The API's `_watch_take_overs` records take-overs that expire. The worker's `record_activity()` logs every tool call and OpenAI `code_interpreter_call` block from the `updates` stream, including helper namespaces, with `ref` = call/block id so replays log once (unique `task_id` + `ref`); hand-offs, approval requests, and schedules are recorded in their own transactions. Hosted code and output are omitted from audit details. Never put raw errors or secrets in `detail`.
- **Usage and budgets** (`tasks/usage.py`): `UsageRecorder`, a LangChain callback in the task's run config, stores every model call's `usage_metadata` as `TaskUsage` (unique task + message id), so helpers and summarization count too; prompt-cache tokens go in `TaskCacheUsage` (keyed by the usage row; `TaskUsage` predates them and has no columns for them). `Budget` rows (`agent`/`channel`, daily tokens, UTC day) are enforced in `next_task()` (tasks stay queued with a "Paused: …" progress), before each model call (`UsageRecorder.on_chat_model_start` raises `BudgetExceeded`), and in `process()` every `BUDGET_POLLS` polls for tasks busy in tools; `stop_for_budget()` cancels and posts a `budget:` system message the watcher publishes. Costs come only from `MODEL_PRICES` (`rate_for()` matches dated ids by alias prefix; cache tokens use cache rates).
- **Schedules** (`tasks/schedules.py`): `Schedule` rows are fired by `fire_due()` in the worker loop; run ids (`schedule-<id>-<run time>`) make firing replay-safe.
- **E2B computer** (`computer/desktop.py`, `computer/e2b.py`, `computer/viewer.py`): `TaskComputer` is an async context manager per task attempt, but the sandbox persists per agent (Band identity) and channel: `computer_key()` is the `TaskSandbox` key, and labels carry workspace/agent/channel ownership. An expired sandbox is replaced with a notice to the agent. Each GUI action consumes a screenshot `screen_id` to make replayed tool calls safe; the computer normally pauses when a task ends. One E2B desktop microVM is used per agent/channel; create enables internet access, private ingress, and timeout auto-pause. The app proxies noVNC WebSockets through short-lived membership-checked links; encrypted ingress tokens stay server-side. A valid `ComputerViewLease` keeps it running for an open 15-minute viewer; explicit Stop overrides that lease, and E2B timeout auto-pause still applies. People reach the same computer through `/api/tasks/{id}/computer/*` (live noVNC link, files, stop): those paths use `ensure(create=False)` and `detach()` so viewing never creates or stops a computer, and an active `ComputerControl` row (take over) makes agent input actions raise `ComputerUnavailable`.
- Raw provider exceptions are kept out of the UI (only the exception type name is stored in `task.error`).

Frontend: React 19 in `frontend/src/` (entry `main.tsx`). Application components are grouped by feature under `components/{agents,chat,computer,documents,generated,settings,shared,workspace}/`; `components/workspace/Workspace.tsx` composes the app shell. Shared API types are in `types.ts`, fetch helpers in `api.ts`, state in `store.ts`, and shared workspace UI types in `components/workspace/types.ts`. Use relative imports within a feature and `@/` imports across features. Task state is refreshed by polling; messages/channel/band-status updates arrive over `/ws`. See `docs/architecture.md` and `CONTRIBUTING.md` for the source map and verification workflow.

Styling is Tailwind 4 + shadcn/ui + Tool UI elements, with no hand-written component CSS:

- `src/app.css` is the only stylesheet: full Tailwind (with preflight), white surfaces and olive accents (`--ui-*` mapped to shadcn names like `primary`, `muted`, `border`, plus `active`, `mention`, `online`, `away`, `chatter`, `warning-bg`, `error-bg`), Geist as `font-sans`, a 16px root with 14px body text, and inline `code` styles. `narrow:` compacts panels at 900px; `sm` utilities handle phone navigation. `WorkspaceNavigation` owns the slim icon rail; `MemberDirectory` and `MemberProfile` provide the members view; `Sidebar` provides conversations. Phone layouts show the list or detail with a back control.
- shadcn primitives live in `components/ui/` (added with `npx shadcn@latest add <name>`); our variants are there too (Button `chip`/`danger`/`link`, sizes `chip`/`inline`/`icon-xs`/`icon-sm`; Badge `tag`).
- Tool UI elements live in `components/assistant-ui/elements/` with shared helpers in `components/assistant-ui/utils/`. Add one with `npx shadcn@latest add @assistant-ui/elements-<name> --yes` (registry in `components.json`), then: move the new element into `elements/`, delete the duplicate `surfaces.tsx` and utils copies the CLI drops next to it (the repo's copies are authoritative; our `surfaces.tsx` has a green `inkButton`), fix its imports, and revert the CLI's edits to `src/app.css`.
- App logic (polling, mention matching, scroll pinning, API calls) stays in our components; the elements are presentational.

## Testing

`tests/conftest.py` points `DATABASE_URL` at a temp SQLite file and blanks `BAND_USER_API_KEY`, `OPENAI_API_KEY`, `E2B_API_KEY`, and `EXA_API_KEY`. Keep tests offline: agent runs use `ScriptedModel` (`tests/test_tasks.py`) injected into the real Deep Agents harness, and computer tests use a fake E2B SDK (`tests/test_computer.py`). Because `settings` is a frozen dataclass read at import time, env overrides must happen before `app` modules are imported (as conftest does).
